# Нагрузка, масштабирование и наблюдаемость

## Результаты замеров

Замерено 04.11.2026 на этом шаблоне (`load/http.js`, `load/ws.js`, k6 2.3.0).

**Условия.** AMD Ryzen 7 7800X3D, но Docker Desktop ограничен **4 ядрами и 8 ГБ**. На этих 4 ядрах одновременно работали все копии API, 2 worker, PostgreSQL, PgBouncer, Redis, Caddy, Prometheus, Grafana, Jaeger и сам генератор нагрузки k6. На отдельном сервере цифры будут выше. Это порядок величин, а не потолок: повторите замер на своём VPS (команды ниже).

### HTTP

Смесь запросов:
- 50 % — котировки (кэш Redis);
- 30 % — список своих сделок (вход + PostgreSQL);
- 15 % — запись сделки;
- 5 % — `/health`.

Нагрузка растёт ступенями до 3000 запросов/с за 100 секунд.

| Конфигурация | Запросов/с (среднее за прогон) | p50 | p95 | p99 | Ошибки | Не успели отправить |
| --- | --- | --- | --- | --- | --- | --- |
| 1 копия API | 1162 | 62 мс | 955 мс | 13 с | 0,21 % | 36 633 запроса |
| **4 копии API** + Caddy + PgBouncer | **1820** (держит пик 3000) | **3,5 мс** | **42 мс** | 129 мс | **0 %** | 724 запроса |

**Выводы:**
- **Предел одной копии.** Одна копия Node упирается примерно в 1100–1200 запросов/с этой смеси.
- **Несколько копий.** Четыре копии за балансировщиком держат пик 3000/с с запасом. Время ответа на сервере (Prometheus): котировки p95 9 мс, сделки p95 39 мс, `/health` 5 мс.
- **Задержка event loop** под пиковой нагрузкой — до 45–50 мс (p99). Это сигнал добавлять копии, а не ждать роста ошибок.

### WebSocket

2000 одновременных клиентов, у каждого 3 подписки (тикеры BTC и ETH, стакан BTC), держат соединение 30 секунд.

| Показатель | Значение |
| --- | --- |
| Подключение, p95 | 14 мс |
| Первое сообщение после подписки, p95 | 16 мс |
| Доставлено сообщений | ~4650 в секунду |
| Пропущено медленным клиентам | 0 |
| Успешных подключений | 100 % (3999 из 3999) |

### Что нашли нагрузочные тесты и что исправлено

| Проблема | Как проявилась | Исправление |
| --- | --- | --- |
| Список сделок без постраничного вывода | p95 7,2 с, через сеть прошло 6,4 ГБ за 100 с: каждый ответ рос вместе с журналом | `GET /api/trades?limit=50&before=<id>`, индекс `(user_id, id)` |
| Лавина промахов кэша | все запросы в момент истечения кэша шли на биржу | один запрос к бирже на копию, остальные ждут его результат |
| Ожидание биржи | котировки p95 222 мс | кэш «отдать сразу, обновить в фоне» (stale-while-revalidate): p95 9 мс |
| Лимит SMS в памяти копии | на 4 копиях лимит фактически ×4 — уязвимость для накрутки SMS | общий счётчик в Redis по IP и по номеру; хранилище Better Auth — в Redis |
| Подделка IP для обхода лимита | без прокси сервер верил `X-Forwarded-For` от клиента | заголовок учитывается только при `TRUST_PROXY=true` (за своим балансировщиком) |

Первый прогон после исправлений: p95 с 7,2 с до 42 мс при той же нагрузке.

## Как повторить

```bash
cd server
# в .env на время теста: RATE_LIMIT_PER_MINUTE=100000000 (иначе лимит 120/мин на IP отклонит k6)
npm run up:scale              # 4 копии API + Caddy + PgBouncer + 2 worker + мониторинг
npm run load:http:scale       # HTTP, до MAX_RPS (по умолчанию 2000) запросов/с
npm run load:ws:scale         # WebSocket, CLIENTS (по умолчанию 2000) клиентов
```

Параметры — переменными окружения: `MAX_RPS=5000 STAGE=60s`, `CLIENTS=10000 HOLD=120`, число копий — `API_REPLICAS=8`. На одной копии без балансировщика: `npm run up` и `npm run load:http`.

Чтобы цифры были честными, запускайте k6 с **другой машины** по сети. Для этого на сервере не должно быть генератора нагрузки, а `BASE` указывайте на адрес сервера.

## Наблюдаемость

`npm run up:monitoring` (или `up:scale`):

| Что | Где |
| --- | --- |
| Grafana, панель «AppJS — сервер» | http://localhost:3001 (admin / admin) |
| Prometheus | http://localhost:9090 |
| Jaeger (трассы) | http://localhost:16686 |

**Метрики (`GET /metrics`).** Prometheus находит все копии API сам, через DNS Docker. Метрики:
- время ответа по маршрутам (p50, p95, p99), ответы по кодам, отказы лимита;
- задержка event loop, CPU и память каждой копии;
- WebSocket: клиенты, сообщения, пропуски, лидер потока биржи;
- очередь BullMQ по состояниям;
- соединения PostgreSQL, Redis.

Снаружи `/metrics` закройте прокси или задайте `METRICS_TOKEN`.

**Трассы (OpenTelemetry).** Включаются переменной `OTEL_EXPORTER_OTLP_ENDPOINT=http://jaeger:4318` или адресом своего сборщика (Grafana Tempo, SigNoz, Honeycomb). В трассах видно входящие запросы по маршрутам, запросы к бирже и Redis. Без переменной трассировка ничего не загружает.

## Масштабирование

```
клиенты → Caddy (балансировщик) → api × N → PgBouncer → PostgreSQL
                                          ↘ Redis: кэш, лимиты, pub/sub WebSocket, очереди → worker × M
```

- **API без состояния.** Копий сколько угодно (`API_REPLICAS`). Caddy раздаёт запросы туда, где меньше соединений, и выводит из ротации копию, у которой не отвечает `/ready`.
- **Node однопоточный.** Тяжёлые вычисления — только в worker (BullMQ), иначе растёт задержка event loop всей копии. Её показывает панель Grafana. Если она растёт — добавьте копии или вынесите работу в worker.
- **PgBouncer** в режиме transaction: сотни соединений копий превращаются в 40 соединений к базе. В этом режиме у драйвера выключены подготовленные запросы (`DB_PREPARE=false`). Миграции идут напрямую в базу, отдельным сервисом `migrate`, один раз до старта API.
- **Дальше по мере роста:**
  - реплики PostgreSQL для чтения;
  - Redis Cluster или Sentinel;
  - балансировщик облака вместо Caddy;
  - Kubernetes — тот же образ, `/health` и `/ready` уже готовы для проверок.
